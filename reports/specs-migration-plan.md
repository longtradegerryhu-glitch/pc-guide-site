## 1. 一句话结论

**迁移的主要工作不是写解析器，是补数据。**

实测 230 个标了「可解析」的字段里，硬命中率 **39.2%**（5395/13773）。schema 共 128 个必填，其中 109 个是 `derive`（能进 dry-run 测），19 个是 `manual`（现库没有，必然是 0）。109 个可解析必填的分布：

| 分档 | 数量 | 含义 |
|---|---|---|
| ≥90% | 33 | 基本现成，解析器直接出值 |
| 60–90% | 34 | 补格式分支即可（`USB3.0×3`、`8G×2`、`十年质保` 这类） |
| 30–60% | 25 | 部分款根本没有这信息，需逐款补 |
| <30% | 17 | 语料里几乎不存在，必须外部核验 |

如果把「解析」当主路径、「解析失败」当异常兜底，会严重低估工作量 —— 107 个可解析必填里有 **40 个**（25+15）硬命中率低于 60%，占 37%；再加上 21 个 `manual` 必填，必须人工补的是 61 个。这不是兜底，这是主线。

---

**2026-10-22 复核追加**：`ssd` 品类实测混入 3 块 3.5 英寸机械盘（紫盘/酷狼/Exos），原 `form` 把 `SATA` 当形态会让它们与固态并列。已拆为 `kind`(SSD/HDD/移动固态) + `form`(M.2 2.5/3.5 英寸 U.2 mSATA 便携) + `iface`(NVMe/SATA/USB)，三个字段均可 derive。

## 2. 目标结构

`specsObj` 与 `specs` **并存**，不是替代：

```js
{
  id: 'u12',
  brand: 'AMD', model: 'Ryzen 7 9700X', name: '...',
  specs: '8核16线程;Zen5;65W;AM5',          // 原字符串，保留，用于降级显示与 diff 审计
  specsObj: {
    _v: 1,                                   // schema 版本，字段含义变了要能识别
    _src: 'derive',                          // derive=解析生成 / manual=人工核验 / mixed
    socket: 'AM5',
    cores: 8,
    threads: 16,
    boostClock: 5.5,
    tdp: 65,
    igpu: '有',
    arch: 'Zen 5'
  },
  specsMissing: ['l3cache']                  // 必填但没值（原字段名 specsParseFail 的落点在这里）
}
```

**四条硬约定**

1. **`_` 前缀是元信息**，不属于规格字段。对比表、筛选器、搜索必须跳过 `_` 开头的键。
2. **`num` 类型存纯数字，不带单位**。单位由 schema 的 `u` 提供，显示层格式化。`65W` 存 `65`，`1TB` 存 `1000`（厂商标称，不用 1024）。
3. **`enum` 必须落在 schema 的 `e` 取值表里**（`open: 1` 的插槽/芯片组除外，但要过白名单正则）。写不进去的值不许塞进 `specsObj`，进 `specsMissing`。
4. **`specs` 永不删除**。它是 `specsObj` 的审计基准：两边不一致时以 `specs` 为准去查 `specsObj` 错在哪。

### 为什么不直接改 `specs` 字符串

- `specs` 是全站唯一的展示来源（首页、配件卡、方案单、AI 问答上下文）。改格式等于同时改 5 处消费方。
- 用户已明确要求「结果页必须给全套部件型号与规格」，`specs` 的可读性不能牺牲。
- 保留原串才能做 **diff 审计**：第 1 批去重删掉重复记录时，要靠 `specs` 原串判断两条记录到底差在哪。

## 3. 三阶段管线

### 阶段 A · 自动解析（覆盖 39.2%）

```
models-data.js (specs 字符串)  →  parse.js  →  specsObj + specsMissing
                                     ↑
                          js/specs-schema.js（字段与单位唯一来源）
                          tools/schema-dryrun.cjs（规则原型，直接长成 parse.js）
```

- 解析器**不使用分号位置索引**。现有位置不可靠：显示器 3~12 段、拓展坞 1~9 段，且「亮度」在 [4] 与 [5] 两处都出现。一律「扫描全部片段 + 按字段规则命中」。
- 输出 `reports/specs-parse-fail.json`，每条含 `{id, catId, missing: [...], raw}`。
- **不写盘到 models-data.js**。阶段 A 产物落在 `_test/specs-obj.json`，跑完整校验闸才合并。

### 阶段 B · 人工补录（覆盖剩余 61.6%）

按分档排序做，不按品类做 —— 因为用户感知最强的是「搜不到」，不是「某品类不完整」。

| 优先级 | 补什么 | 依据 |
|---|---|---|
| P0 | 15 个 <30% 的必填字段 | 语料里没有，只能外部核验 |
| P0 | 所有 `s` 搜索词对应的字段 | 这是 ORD-06 的核心诉求：字段存在但搜不到等于没做 |
| P1 | 25 个 30–60% 的必填字段 | 逐款补，工作量最大 |
| P2 | 30 个标 `manual` 的字段（含 21 个必填） | 不阻塞对比表 |
| P3 | 37 个 60–90% 的补分支 | 纯解析工作，成本低，可批量 |

补录写进哪？**不直接改 models-data.js**。新建 `_test/specs-patch/*.js`，格式：

```js
// _test/specs-patch/ssd-form.js
module.exports = {
  'ssd-u12': { form: 'M.2', length: 80 },
  'ssd-u13': { form: 'SATA' }
};
```

`build_models.js` 链条末尾加一步 `apply_specs_patch.js` 合并。理由与现有 `plus_*.js` 一致：**直接改 models.js 的补丁重建必被冲掉**，必须固化成链条中的一步。

### 阶段 C · 校验闸（并入现有四层测试）

新增三条断言，全部可变异自测：

| 断言 | 判据 |
|---|---|
| `specs:req-missing` | 必填字段在 `specsObj` 里缺失的条目数 ≤ 基线（分品类计数） |
| `specs:enum-valid` | `enum` 值必须在 schema 取值表内（`open` 的走白名单） |
| `specs:unit-sanity` | `num` 值落在物理合理区间（如 `refresh` 0–1000、`tdp` 1–1500、`size` 1–120），超界报错 |

第三条是关键：解析器最容易把「4K」抽成 refresh=4 或把「27英寸」抽成 tdp=27。没有量纲校验，错值会静默进入对比表，比缺失更难发现。

## 4. 实测发现的六个坑（迁移时必须处理）

### 坑 1 · 中文数字

`十年质保` / `五年质保` / `三年`。我第一版规则只写 `(\d+)年`，`psu.warranty` 覆盖率 8/53；补中文数字后 24/53。**所有带「年/天/小时」的字段都会踩**（质保、续航、寿命）。

映射表：`一二三四五六七八九十两` → 1–10，`十一~十九`、`二十`、`三十` 需组合规则。

### 坑 2 · 值在前，单位在后

三种写法并存，正则方向要覆盖全部：

| 字段 | 写法 A | 写法 B | 写法 C |
|---|---|---|---|
| 内存容量 | `32GB` | `16G×2`（单条×条数，要相乘） | `16GB(单条)` |
| USB 口 | `2×USB-A` | `USB3.0×3` | `USB-C 1 个` |
| 热管 | `6 热管` | `6×6mm 热管` | `六热管` |
| 频率 | `6000MHz` | `最高 5.2GHz` | `5.2G` |

`8G×2` 是**单条 8G × 2 条 = 16G 总容量**。第一版规则把它当容量 8 读，52 款内存里只有 12 款能出值。这类算术字段（容量、套装数）必须有专门分支，不能靠单一正则。

### 坑 3 · 一格多值

`ATX/MATX/ITX`（一机箱支持三种板型）、`360/280/240`（冷排支持）、`2×HDMI2.1 + 1×DP1.4 + USB-C 90W`（接口组合）。

这些字段在 schema 里标了 `text` 而不是 `enum`，是**故意的**：一格多值无法用单值枚举表达，硬塞枚举会产生假值。对比表里它们只展示不排序。

### 坑 4 · TB 与 GB 混用

`1TB` / `1T` / `1000G` / `1024GB` 四种写法。统一存 GB，换算用 **1000**（厂商标称），不用 1024。存 1024 会让「1TB 盘」和「1024GB 盘」在对比表里显示成两个不同规格。

### 坑 5 · 「无」和「没写」不是一回事

`无核显` / `无独立缓存` / `不防水` 是**确定的值**，`没写` 是**缺失**。前者要落值（`igpu: '无'`），后者进 `specsMissing`。混在一起会让「搜无核显」召回所有没写核显信息的款。

判定办法：schema 的 `e` 里如果含「无/不支持/不防水」这类否定取值，解析时必须先匹配否定词，再匹配肯定词。

### 坑 6 · 体积

1209 条 × 平均 12 字段。若全量结构化，`models-data.js` 会从 760KB 涨到约 1.1MB（+45%）。

对策：
- `text` 类字段（主控、材质、接口组合）**不复制进 `specsObj`**，展示时从 `specs` 读。它们本来就不参与对比。
- 只对 `num` / `enum` / `bool` 落 `specsObj`，字段数从 258 降到约 170。
- 若仍超预算，`specsObj` 拆成独立文件按品类懒加载（`js/specs-obj/<catId>.js`），主页不加载。

## 5. 分品类建议顺序（不按品类编号，按「修一次能救多少搜索」）

我做了一次搜索召回实测，这三个品类修一个字段就能救回 20+ 款的召回：

| 品类 | 缺的字段 | 现状 | 补齐后 | 差 |
|---|---|---|---|---|
| 固态硬盘 | `form`（M.2/SATA/U.2） | 搜 `M.2` 召回 SSD **24** 款 | **43** 款 | +19 |
| 笔记本电脑 | `iface` / `thunderbolt` | 接口在 specs **0/79**，雷电仅 8 条出现在软文本 | 79 款全部有值，可筛「有雷电」 | 字段从无到有 |
| 平板 | `keyboard` / `stylus` | 键盘在 specs **0/66**，软文本 39 条、触控笔 29 条 | 至少 39 款可按「能接键盘」筛 | +39 |

其次：支架 `vesa`（3/40 → 靠外部核验补）、手机 `ipRating`（1/93）、耳机 `bluetooth`（20/95）。

这三个品类做完，「搜不到规格」的用户感知差异最大，建议作为阶段 B 的第一批。

## 7. 需要总控拍板的三个判断点

这三件事我按自己的判断给了默认方案，但会影响第 1 批与第 4 批的边界，所以摆出来说明我的选择和回退成本。

### 7.1 `specsObj` 是「新字段」还是「替换 specs」

**我的选择**：新增字段，`specs` 保留。
**理由**：`specs` 是 5 处消费方的唯一来源，替换等于同时改首页、配件卡、方案单、AI 上下文、SEO。保留的成本只是一份数据冗余（约 +45% 体积，见坑 6），换来的是可回退。
**回退方式**：若确认要替换，删除 `specs` 字段即可，消费方改读 `specsObj` 的格式化输出（`fmtSpecs(catId, obj)` 一个函数）。

### 7.2 覆盖率 39.2% 是否可接受

**我的选择**：接受，但把它写进验收基线，不许倒退。
**理由**：ORD-06 预设「解析不出的进 specsParseFail 人工补」，隐含假设是失败是少数。实测是 61.6%。如果按「解析为主」排期，第 1 批会严重超期。
**这条是本次最重要的反驳**，详见反馈第 3 节。

### 7.3 品类合并（`input` 键鼠 / `audio` 音箱麦克风 / `wearable` 混杂）

**我的选择**：不合并品类，在 schema 里加 `kind` 字段做子类型分流。
**理由**：品类 id 已被 `LOOKS`、`topList`、`device` 分区、`plans` 引用，改 id 会牵动至少 9 处。`kind` 字段是纯增量。
**代价**：`kind` 是 `manual`（现库没有），必须先补 68 + 37 + 71 条的类型判定，否则对比表在这些品类上无法分组。

## 9. 第 1 批执行记录（2026-10-22，ORD-14）

**结论先说：阶段 A 已经跑完并把产物写进了 `js/models-data.js`，与本文原方案有三处不同。**

| 原方案 | 实际做法 | 为什么改 |
|---|---|---|
| 产物落 `_test/specs-obj.json`，不写盘到 models-data.js | 直接写回 `js/models-data.js` 的 `specsObj` | 不写盘的话浏览器读不到，`matchQuery` 就没法接线，第 0 批的 schema 等于零收益。写回是幂等的（`node tools/derive-specs-obj.cjs --check` 可验证） |
| 解析器新写 `parse.js` | `tools/specs-derive.cjs`，dryrun 反过来调用它 | 两套正则必然漂移：dryrun 说 53/53、迁移填不出值，这种「闸说好、实现做不到」是 ORD-11 返工的根因。现在命中判定与取值是同一份代码 |
| 阶段 A 覆盖全部 21 品类 | 只做 `ssd` + `laptop.iface` + `tablet.keyboard/stylus` | ORD-14 明确限定三个品类，其余留第 3 批 |

### 9.1 三个品类的实际结果（与 ORD-14 的预期不同）

| 品类 | 字段 | 覆盖 | 说明 |
|---|---|---|---|
| `ssd` | 11 个 | 5 个 100%，其余 83%~94%；`seqWrite` 7/53、`tbw` 8/53 | 全库唯一真正可解析的品类 |
| `laptop` | `iface` | **0/79** | 79 款 specs 是固定 5 段模板（CPU;内存;SSD;屏幕;重量），**一个接口字样都没有** |
| `tablet` | `keyboard` / `stylus` | **0/66 / 0/66** | 66 款 specs 同样不含笔/键盘 |

后两个不是规则不够，是**信息根本不在 specs 里**。它们只出现在 `compat` / `valueNote`：

- `tb1`「网课平板，配**笔式支架**与屏幕保护膜」——「笔」指的是支架形态，不是手写笔支持；
- `tb13`「需另购 Apple Pencil」——是采购建议，不是本机规格；
- `lt1`「配 Type-C 拓展坞即可补齐接口」——说的是要买拓展坞，不是本机有 Type-C。

**从 `compat` 抽硬字段会直接造出假值**，所以这三处一律留空，进 `specsMissing`。这是对 ORD-14 第 2 条的一处反驳，见 `FEEDBACK/执行者.md`。

### 9.2 `ssd.form` 从 53/53 降到 50/53 是修正，不是倒退

上一轮把 `/SATA/` 也算作形态命中，等于把接口当形态 —— 那正是我自己在 ORD-06 反驳里指出的错误。3 款纯 SATA 固态（`sd13`/`vd13`/`vd14`）的 specs 只写接口不写尺寸，形态确实未知，进 `specsMissing`。全库覆盖率仍从 38.9% 涨到 39.2%。

### 9.3 低覆盖必填字段对账

见 `reports/specs-field-reconcile.md`：42 个必填且 <60% 的字段里，**6 个是规则分支不足**（补规则合计净增 81 条命中），**36 个是真缺**。工期不能按 42 个算。
